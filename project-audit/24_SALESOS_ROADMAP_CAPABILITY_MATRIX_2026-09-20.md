## 1. Reading the status

| Label | Meaning |
|---|---|
| **BUILT** | Relevant implementation exists in the current checkout. This does not by itself mean the full user flow works or is production-ready. |
| **PARTIAL** | Some code, data model, API, UI, or tests exist, but the described product capability is incomplete or disconnected. |
| **UI ONLY** | A route or screen exists; the complete persisted business capability is not evidenced. |
| **BACKEND ONLY** | A service/API/model exists, but a usable product experience or end-to-end wiring is missing. |
| **MISSING** | No implementation evidence was found for the stated capability in the reviewed paths. |
| **UNKNOWN** | The checkout or available evidence does not establish the state. |

“Tested” is reported separately from code presence. A test file is not a passing test; previously documented test results are identified as historical/scoped evidence. ## 2. Executive assessment

**The repository has a broad product and platform foundation, but not yet a proved Revenue OS.** The roadmap’s short path—trusted account data → evidence-backed signal/recommendation → human approval → real CRM action → measured outcome—remains the correct first product proof. The broader Market, Leadership, Customer Success, attribution, and learning capabilities are uneven: some have real services or screens; others are fixture-based, disconnected, or future scope.

The full frontend Jest regression passes **318/318 suites (2,643 passed, 1 skipped)** after the page-exit telemetry change. The later Fact Review follow-up reconciled the shared decision contracts and legacy consumers: full frontend TypeScript now passes in the matched C: verification copy, and the Next production build exits 0 with **111/111** routes generated. A non-fatal `EPERM` warning appears only while standalone tracing follows the mirror's linked `node_modules`. Authenticated page-exit persistence, live Fact Review JWT/RBAC, and customer use remain unverified.

The newer code materially updates some older audit claims. For example, the old Odoo row in the 2026-09-20 snapshot of `11_CAPABILITY_MATRIX.md` says Odoo is not started beyond a migration/config placeholders. The current checkout contains an Odoo adapter, routing, feature-flag gating, sync code, and Odoo-focused test files. That establishes **implementation present and tests authored**, not successful test execution or live/production connectivity. This matrix records the current files and leaves live readiness unknown.

### Highest-impact findings

1. **Product telemetry now has a persistent, authenticated, idempotent code path.** The frontend uses the authenticated SalesOS API client and generates a UUID per event. The event receiver writes normalized events through `TelemetryService` into `telemetry_events`, using request-authenticated user identity and tenant RLS; unique `(tenant_id, client_event_id)` storage deduplicates retries. Passive events are batched; accept/reject/execute/outcome events flush immediately. The CSRF cookie is warmed during tracking; `pagehide` resends queued and unconfirmed events with authenticated Fetch `keepalive`, retaining event IDs for server deduplication. Focused tests plus signed ASGI HTTP replay and an authenticated `salesos_test` browser/read-back pass for view, execution, and outcome. Browser read-back for acceptance/rejection telemetry and actual page-exit delivery remain open; partner use is unverified.
2. **Evidence scoring now follows ADR-0113 for fully classified evidence.** Python and TypeScript implement the same kind weights, noisy-OR combination, 0.99 ceiling, and 0.45 contradiction cap. Account/Deal Intelligence now classifies its CRM-derived records as non-primary `crm.system_of_record` evidence at a provisional 0.55 weight. Provider/model `confidence` remains separate. Eight shared Python/TypeScript golden vectors now prove parity for scorer outputs, including source de-duplication and caps. A compatibility defect that dropped untyped legacy items from mixed insights is fixed: ADR-0113 now applies only when every item is classified; otherwise all evidence remains in the explicitly marked legacy average. Remaining work is broader producer classification, field-decision/write-boundary alignment, freshness, and point-in-time behavior.
3. **NBA execution now creates an idempotent CRM task and audit record.** Completion updates the linked task. Exact tenant-local company matches link the task; ambiguous or missing matches leave it unlinked. No email/WhatsApp is sent and no opportunity is created automatically. Unit tests and an isolated database-backed tenant-isolation trace pass.
4. **Time fields exist, but no common temporal standard is evident.** Master Data has observed/superseded timestamps and other modules store event or source timestamps; the cross-domain “what was known when this decision was made?” contract is not established.
5. **Production readiness is not established.** Master Data browser verification is test-database evidence, Phase 7 is blocked, Copilot defaults off, Agent Reach is not configured, and the audit explicitly keeps production not approved.
6. **Recommendation confidence and action fit are distinct measures.** The TypeScript decision-platform lab twin previously returned the selected action score as confidence. It now bounds confidence by the reliability of the action's input scores and passes 118/118 package tests. The package README explicitly says the twin is not wired to the frontend resolve path and is not GA. The governed Decision Center tests pass 51/51; its ledger receives confidence from its decision producer/ensemble path, so producer-level evidence lineage and calibration remain open.
