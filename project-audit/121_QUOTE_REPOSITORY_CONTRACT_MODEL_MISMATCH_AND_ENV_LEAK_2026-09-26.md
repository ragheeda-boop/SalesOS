# 121 — PostgresQuoteRepository: guaranteed crash on every real call (same bug class as report 120), plus a live near-miss that actually leaked 2 rows into the persistent dev database

**Read-only in scope of production/salesos_test.** Fix verification ran against a disposable, ephemeral `pgvector/pgvector:pg16` container migrated to the current Alembic head, torn down after use. No write to `salesos_test` or production. A real, if narrow, incident occurred against the persistent local dev database during this session's own verification work — fully disclosed and remediated in §3 below.

## 1. Reachability — live, same wiring pattern as report 120

`domains/commercial/infrastructure/postgres_repositories.py`'s `PostgresQuoteRepository` is instantiated by `app/routers/commercial.py`'s `_get_quote(db)` factory (`QuoteService(PostgresQuoteRepository(db))`), used by real mounted endpoints. Every real call to `QuoteService.create_quote()` / `add_line()` / `submit_for_approval()` / `approve()` / `send()` / `accept()` — i.e. the entire quote lifecycle — would have crashed on its first `self._repository.save(quote)`.

## 2. Bugs — same class as report 120's `StageEntry`, found via continuing the mypy sweep

The `Quote` domain contract (`domains/commercial/quote/contracts/models.py`) has `lines: list[QuoteLine]`, `approval: ApprovalState` (nested `approved_by`/`approved_at`), and computes `grand_total` from `lines` as a property — there is no top-level `total_value`/`sent_at`/`approved_by`/`approved_at`/`accepted_at`. `QuoteModel` (table `commercial_quotes`, FORCE RLS) denormalizes exactly those workflow fields as flat columns instead.

- `save()` read `quote.total_value`, `quote.sent_at`, `quote.approved_by`, `quote.approved_at`, `quote.accepted_at` — none exist on the contract. **`AttributeError` on every call**, confirmed below.
- `get()` / `get_by_opportunity()` / `list_by_tenant()` constructed `Quote(total_value=..., sent_at=..., approved_by=..., approved_at=..., accepted_at=...)` — keyword arguments the constructor does not accept.
- **A second, independent bug**: `quote.lines` (the line items — the actual substance of a quote) were never persisted at all. `save()` never touched `commercial_quote_lines`. `QuoteService.add_line()` — a real, directly-exercised service method — appends to `quote.lines` and calls `save(quote)`; without line persistence, every added line would silently vanish on the next load, even if the crash above were somehow avoided.
- `revenue_kpis()` constructed `QuoteRevenueKPIs(total_accepted_value=..., accepted_count=..., conversion_rate=..., average_value=...)` — none of these are the contract's real field names (`total_quote_value`, `accepted_quotes`, etc. — mypy's own suggestions named the correct fields exactly). Zero live callers reach this method today (confirmed via grep — only `QuoteService.revenue_kpis()` delegates to it, and only a domain-level unit test exercises it, against the in-memory repository), but fixed anyway since it was already being touched and the reference implementation (`in_memory_repo.py`) made the correct formulas easy to mirror exactly.

## 3. Fix

- `save()`: upserts by id (mirroring report 120's pattern). Maps `quote.grand_total → model.total_value`, `quote.approval.approved_by/approved_at → model.approved_by/approved_at`. `sent_at`/`accepted_at` have no equivalent field on the contract at all — inferred via status-transition detection: when the persisted status differs from the new status and the new status is `SENT`/`ACCEPTED`, the corresponding timestamp is set to `quote.updated_at` (which every lifecycle method in `QuoteService` — `send()`, `accept()` — already sets to "now" immediately before calling `save()`). This is not fabricated history; it records "this transition is being persisted now," matching exactly how the service methods use it.
- New `_sync_lines()`: upserts/deletes `QuoteLineModel` rows to match `quote.lines` by id.
- `get()` / `get_by_opportunity()` / `list_by_tenant()`: reconstruct through one `_to_domain()` (now `async`, since it loads lines) using the contract's real field names and shape (`ApprovalState(approved_by=..., approved_at=...)`, `lines=[...]`).
- `revenue_kpis()`: reuses `list_by_tenant()` and mirrors the in-memory repository's exact KPI formulas field-for-field, keeping both repository implementations contract-aligned (matching the documented convention already used by `PostgresPipelineRepository.compute_kpis()` in the same file).
- A separate, already-flagged bug in the same lifecycle (`QuoteService._record_approval_audit()`, called from `approve()`): `from sdk.database import async_session_factory` — no such attribute exists in `sdk/database.py` at all, so this import always raised `ImportError`, silently swallowed by the method's own bare `except Exception: pass`. The "P1-9 domain-specific approval audit trail" (a compliance-relevant feature per its own docstring and this codebase's history) had therefore likely never recorded a single entry. Fixed to `from app.database import apply_tenant_guc, async_session`, with the tenant GUC now pinned before the insert (`audit_logs` is a FORCE-RLS tenant table) — matching the pattern this session has applied repeatedly (reports 121→136 in the earlier numbering, DEC-157, etc.).

**Not fixed, disclosed**: `commercial_quote_lines` has only `description`/`quantity`/`unit_price`/`total` — no `discount_percent`/`tax_percent`/`description_ar`/`product_code`/`notes` columns, so those per-line fields do not round-trip through this schema. A pre-existing persistence-schema limitation (same category as report 120's `exit_reason` gap), not introduced here, not silently papered over with fabricated values.

## 5. A real near-miss during this session's own verification — disclosed and fixed

While re-running a Ruff check immediately after the fix, one `python -m pytest` invocation was issued **without** re-exporting `DATABASE_URL`/`APP_POSTGRES_PASSWORD` in that same shell call (Bash tool shell state does not persist between separate tool calls — a discipline this session already knew from report 118, and slipped on here). This silently repeated report 118's exact exposure: `app.database.engine` resolved to `localhost:5432/salesos` — the persistent local dev Postgres — instead of the intended disposable container.

Unlike report 118 (caught before any write), this time a **real write actually happened**: the test's own mid-test `await session.commit()` (used to seed a tenant before the main transaction) persisted a tenant row (`id=26c7d305-6787-4e72-9233-ef8b7502fc4a`, name "Quote Test") to the real `salesos` database, and — independently — `_record_approval_audit()`'s newly-fixed code path opened its **own separate session with its own explicit commit**, persisting one `audit_logs` row (`action=quote.approved`) tied to that same tenant, before either the outer test's later rollback could undo anything.

**Immediately checked and confirmed**: `commercial_quotes` and `commercial_quote_lines` had zero rows for this tenant (the outer transaction's rollback did correctly undo those). Only the two explicitly-committed writes leaked. Both were deleted directly (`DELETE FROM audit_logs WHERE tenant_id = ...`, `DELETE FROM tenants WHERE id = ...`), confirmed empty afterward. No other test file's stray tenants were found on the same check.

**Fixed at the source**: added the same `current_database() != "salesos"` refusal fixture (from report 118) to both `test_quote_repository_persistence_db.py` and `test_pipeline_stage_entry_persistence_db.py` (report 120's test, which had not yet received this guard either). Verified the guard actually works — running either file with no env override now fails immediately in fixture setup (before touching any table), confirmed via a second no-env-var run that left zero new rows in the persistent database.

**A second, unrelated bug surfaced while adding the guard**: both test files originally used a `def test_...(): asyncio.run(_run())` wrapper (copied from an unrelated sibling test that needs it for a different reason — running `TestClient` alongside `asyncio.run()`). Combined with the new `pytest_asyncio.fixture(autouse=True)` guard, this created two different event loops for the same test (fixture running in pytest-asyncio's loop, test body in its own fresh `asyncio.run()` loop) sharing the same process-global `engine` — `RuntimeError: ... attached to a different loop`. Fixed by converting both test functions to plain native `async def test_...():` (this repo's `pyproject.toml` sets `asyncio_mode = "auto"`, so no decorator is needed), matching the pattern already used correctly by `test_feature_store_licenses_table_db.py`. Re-verified both fixed tests pass individually and together in the same pytest invocation.
