## 3. Root Cause

### Primary: Credential rotation / redeploy caused staging DB unavailability

During a staging deployment, the PostgreSQL credentials or connection string changed (likely due to Railway credential rotation or a redeploy that re-provisioned the database service). This caused:

1. **Connection pool exhaustion** — all in-flight requests to staging DB failed
2. **Auth failures** — `asyncpg` could not authenticate with the new credentials
3. **No auto-recovery** — the soak loop had no retry/backoff for transient DB outages

### Contributing: `init_db()` detection-only behavior

The staging `preDeployCommand` uses `python -c "... init_db() ..."` which:
- **Detects** schema drift (logs warning)
- **Does NOT auto-migrate** (safety control B03-B)
- **Does NOT verify** DB connectivity before accepting traffic

This meant the deploy succeeded (exit code 0) while the DB was unreachable, creating a silent failure window.

### Why 97.6% of failures were in one window

The 80 failures concentrated in a ~7h window because:
- The soak loop runs continuously (iterations every ~5 minutes)
- During the outage, every iteration failed
- After restoration, the loop resumed passing — no cascading failures
