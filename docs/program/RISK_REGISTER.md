# Risk Register

> **Canonical source** for every program risk (R-01 through R-10) and every constraint-derived risk referenced elsewhere in this program (`MASTER_EXECUTION_PLAN.md` §7, `IMPLEMENTATION_SEQUENCE.md` §9/§6, sprint files under `SPRINT_PLAN/`). Those documents cross-reference risk IDs from here rather than redefining them — if a risk's likelihood, impact, or mitigation changes, update it **here first**.
> **Scoring:** Likelihood (1-5) × Impact (1-5) = Score. Score ≥15 is escalated to CTO/CPO review at the next phase gate regardless of mitigation status.
> **Status values:** `Open` (actively unmitigated), `Mitigating` (mitigation in progress, tracked against a specific sprint), `Monitoring` (mitigation shipped, watching for recurrence), `Closed` (mitigation verified, risk retired).

## Highest-Priority Cluster (Score ≥15)

R-04, R-08, R-09, R-11 (16), R-01 (15, now closed) are **all Phase 0 items** — this is the entire justification for Phase 0 (`PRODUCT_ROADMAP.md` Phase 0) existing as a dedicated, non-skippable phase before any commercial feature work begins.

**R-14 (score 25) is the highest-scored risk in this entire register**, discovered during Sprint 02's STORY-02-01 hand-test. It is scored higher than everything else because it was not a probabilistic risk — it was a confirmed, present-tense fact about the database configuration (`salesos` is a superuser with BYPASSRLS) that made Sprint 03's stated Phase 0 exit criterion ("100% of 72 tenant-scoped tables have an RLS policy; adversarial suite passes 100%") unachievable in any meaningful sense. **Now partially closed** — local dev, CI, staging, and the self-hosted production template are all remediated and independently verified (see the R-14 row for full detail); **Railway is the sole remaining open environment**, left untouched per explicit user decision rather than guessed at. The score stays 25 in this table as the historical record of what was found, not retroactively softened; the Status column is what reflects current reality. Sprint 03's Phase 0 exit gate cannot be marked fully green until Railway specifically is remediated and verified, or the program formally accepts shipping without Railway covered (a decision for whoever owns that call, not assumed here).

**R-15 (score 20, closed same session) was the second-highest score this register has ever carried** — a live, exploitable cross-tenant IDOR in `app/routers/meetings.py`, discovered opportunistically (not part of any assigned story) while picking a demonstration target for STORY-01-04, and fixed the same session under the Sprint Execution Contract's small-fix carve-out rather than left open pending a future sprint. Recorded here at its full pre-fix severity, not retroactively downgraded, so the register reflects what was actually found, not just what remains.

## Escalation Rule

Any risk scoring ≥15 that is still `Open` (not `Mitigating` or better) at its designated phase gate automatically blocks that gate's Go/No-Go decision — per `IMPLEMENTATION_SEQUENCE.md` §10 Decision Gates, this requires Program Director + the risk's named Owner to jointly present a revised mitigation plan before the gate can pass, rather than the gate silently proceeding.

## Adding a New Risk

Any newly discovered risk during execution (a Sprint's "Technical Debt Identified" note, a postmortem finding, a chaos-drill discovery) gets assigned the next sequential ID (`R-11`, `R-12`, …) and added to the table above — never silently tracked only in a sprint file or a postmortem doc, since this register is the single place `MASTER_EXECUTION_PLAN.md` and `IMPLEMENTATION_SEQUENCE.md` expect to find the complete, current set.
