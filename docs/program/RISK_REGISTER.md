# Risk Register

> **Canonical source** for every program risk (R-01 through R-10) and every constraint-derived risk referenced elsewhere in this program (`MASTER_EXECUTION_PLAN.md` §7, `IMPLEMENTATION_SEQUENCE.md` §9/§6, sprint files under `SPRINT_PLAN/`). Those documents cross-reference risk IDs from here rather than redefining them — if a risk's likelihood, impact, or mitigation changes, update it **here first**.
> **Scoring:** Likelihood (1-5) × Impact (1-5) = Score. Score ≥15 is escalated to CTO/CPO review at the next phase gate regardless of mitigation status.
> **Status values:** `Open` (actively unmitigated), `Mitigating` (mitigation in progress, tracked against a specific sprint), `Monitoring` (mitigation shipped, watching for recurrence), `Closed` (mitigation verified, risk retired).

## Escalation Rule

Any risk scoring ≥15 that is still `Open` (not `Mitigating` or better) at its designated phase gate automatically blocks that gate's Go/No-Go decision — per `IMPLEMENTATION_SEQUENCE.md` §10 Decision Gates, this requires Program Director + the risk's named Owner to jointly present a revised mitigation plan before the gate can pass, rather than the gate silently proceeding.

## Adding a New Risk

Any newly discovered risk during execution (a Sprint's "Technical Debt Identified" note, a postmortem finding, a chaos-drill discovery) gets assigned the next sequential ID (`R-11`, `R-12`, …) and added to the table above — never silently tracked only in a sprint file or a postmortem doc, since this register is the single place `MASTER_EXECUTION_PLAN.md` and `IMPLEMENTATION_SEQUENCE.md` expect to find the complete, current set.
